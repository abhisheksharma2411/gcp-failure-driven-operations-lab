# risk-gated-release

Companion lab for **Article 4 — The One-Line Configuration Change That Takes
Down the World**.

```bash
make verify
```

28 tests, no cloud project, no credentials, no network.

## What this proves

On 2 July 2019 a Cloudflare WAF rule update "went global in seconds" and took
the network down for 27 minutes. Their own remediation is this lab's premise:

> "Changing the SOP to do staged rollouts of rules in the same manner used for
> other software."

The failure was not the regular expression. It was that a change classified as
*configuration* did not get the staging that a change classified as *code*
already had.

So this module derives required gates from **blast radius**, not change type.
`T1` asserts that every change type at global radius carries the same seven
core gates. `T3` asserts that requirements increase monotonically with radius,
so no combination can be quietly cheaper than a smaller one.

## The measured result

| Scenario | Outcome | Max traffic exposed |
|---|---|---:|
| Gated, healthy | COMPLETED | 100% |
| Gated, error-rate regression at the first phase | HALTED | 25% |
| Gated, business check fails at the first phase | HALTED | 25% |
| Manifest blocks the ungated change | BLOCKED_AT_GATE | 0% |
| **No manifest at all, broken change** | HALTED | **100%** |

The last row needs the gate to be *absent* rather than failed. Running an
ungated change through the gated path simply blocks it, which is the manifest
working rather than the failure being reproduced — a distinction the first
version of this report got wrong.

## The gate that gets skipped

`N3` is worth reading. The same change is observed with an error rate of 0.001,
a p99 of 190ms against a 200ms baseline, and a failing business check. Every
technical signal says healthy. With the business check the rollout halts at 25%
exposure; without it the change reaches everything.

A service can be up, fast, returning 200, and wrong.

## The manifest

`make report` emits `results/release-risk-manifest.json`, which is the
machine-readable artifact a pipeline would consume:

```text
matrix[changeType][blastRadius] -> required gates
emergency_path                  -> the narrow exception, never anonymous
```

Gate counts by type and radius:

| Change type | single-instance | single-region | global |
|---|---:|---:|---:|
| `application-code` | 2 | 6 | 8 |
| `configuration` | 2 | 6 | 8 |
| `infrastructure` | 2 | 6 | 8 |
| `schema` | 3 | 7 | 8 |
| `iam` | 3 | 7 | 8 |
| `routing` | 2 | 6 | 8 |
| `edge-policy` | 3 | 7 | 8 |

Everything converges at global radius. That is the design, not a coincidence.

## What this lab is not

It does not deploy anything. There is no Cloud Deploy pipeline, no Cloud Build
trigger, and no Binary Authorization policy attached to a real cluster. It
models the *decision* a release system makes, which is the part that was wrong
in 2019, and it does so deterministically at zero cost.

`policy/cloud-armor-preview-example.md` shows the real commands for the one
gate that is nearly free to adopt, including the recovery step most teams skip.

## Layout

```text
src/
  manifest.ts   gates by radius and type; the emergency path
  evaluate.ts   the promote/block decision, with an audit record on both paths
  rollout.ts    staged phases, halting, and the ungated comparison
tests/
  manifest.test.ts         T1-T14
  rollout.test.ts          T15-T23
  negative-control.test.ts N1-N5
docs/adr/       three decision records
policy/         a worked Cloud Armor preview example
results/        generated by `make report`; never edited by hand
```
