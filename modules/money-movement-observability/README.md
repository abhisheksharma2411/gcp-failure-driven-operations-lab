# money-movement-observability

Companion lab for **Article 22 — Observability for Money Movement on Google
Cloud**.

It instruments a small synthetic money-movement flow — four services, one
logical payment, a provider effect, a double-entry posting group and a
settlement record — and then asks eighteen questions of it. The one that
matters is scenario **S04**: every HTTP call returns 200, p95 latency is 42 ms,
the error rate is zero, every technical objective is met, and the journal is
short by exactly the provider's fee.

```bash
make verify     # strict typecheck, 68 tests, report, definitions drift check, secret scan
make report     # regenerate every table in the article
make incident   # walk one incident: alert, diagnosis, repair, verification
node scripts/incident.ts --help
```

No cloud project, no credentials, no network, no billing account.

## What it contains

| Piece | Where | What it is |
|---|---|---|
| Trace model | `src/telemetry/trace.ts` | Spans, W3C `traceparent` propagation, head sampling keyed on the trace ID |
| Structured logs | `src/telemetry/logs.ts` | Correlation fields and write-time redaction |
| Metric registry | `src/telemetry/metrics.ts` | A cardinality guard that refuses an undeclared label value |
| Audit trail | `src/telemetry/audit.ts` | Append-only, unsampled, separate from the trace |
| The flow | `src/domain/flow.ts` | Four instrumented services and twelve injectable faults |
| Invariant catalogue | `src/invariants.ts` | Eight business invariants, evaluated out of band from durable state |
| SLO catalogue | `src/slo.ts` | Five tiers; the ledger and settlement tiers are detect-and-repair, not ratios |
| Alert rules | `src/alerts.ts` | Fourteen rules, each with a route and a runbook |
| Fault catalogue | `src/scenarios.ts` | Eighteen scenarios as data, with their expected signals |
| Incident loop | `src/incident.ts` | Alert, diagnosis, idempotent repair, verification, evidence |
| Dashboards as code | `src/dashboard.ts` | Two dashboards, exported with a drift check |
| Telemetry volume | `src/cost.ts` | Bytes and series. No prices appear anywhere |

## The result that matters

From `results/report.md`, regenerated by `make report`:

| scenario | technical SLOs | invariants violated | alerts fired |
|---|---|---|---|
| **S04** every call returns 200 and the journal is short by the fee | all green | **INV-1** | ALERT-LEDGER-IMBALANCE |

**8 of 18 scenarios leave every technical objective green while a business
invariant is violated.** Three more are green with nothing financially wrong
and still page somebody: those are the cases where the telemetry itself has
stopped working, and a green dashboard means nothing is looking.

*Simulated result.* Deterministic: there is no `Date.now()` in `src/`, every
identifier comes from a seeded counter, and `make report` is byte-identical on
re-run.

## Structural checks that are tests, not review comments

- **Every alert must be fired by at least one scenario.** The first run of this
  check found seven rules no exercise could trigger. Seven scenarios were added
  until the list was empty.
- **Every scenario that violates an invariant must fire at least one alert.**
- **Every invariant must be named by at least one objective**, and every
  invariant's runbook must be routed to by an alert.
- **Every metric must appear on a dashboard**, or it should be deleted.
- **No declared metric label may be an investigation key.**
- **Five mutations must each turn specific, named scenarios red**, and a
  mutation blunt enough to redden the whole catalogue is rejected.
- **A scenario with a deliberately wrong expectation must fail**, or every
  other assertion passes vacuously.

## Scope

This module models the *shape* of a money-movement observability stack. It is
not a Google Cloud client: it creates no resources, calls no API, and holds no
credentials. `docs/MODEL.md` lists every way it departs from real platform
behaviour, including the ones that flatter it.

Boundaries with the rest of the portfolio: Article 7 owns reconciling duplicate
and late events into a financial position; this module owns noticing that the
position is wrong. Article 6 owns recovery evidence. Article 4 owns how changes
reach production. Article 12 owns the idempotency contract whose closing rule —
count effects, not arrivals — is the reason `money.effects.applied` exists
beside the request counters.
